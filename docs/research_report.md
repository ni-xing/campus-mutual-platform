## 2. 事实：标杆系统盘点和方案详述

### 2.1 行业标杆清单

**硬指标**：≥ 3 家；至少包含 1 家头部 SaaS 代表 + 1 家开源/自研代表。本报告盘点 4 家（B1/B2 为头部 SaaS，B3/B4 为开源/自研代表）。

| 编号 | 标杆系统 | 厂商 / 社区 | 部署形态 | 场景覆盖 | 技术亮点 | 商业模式 | 调研来源 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| B1 | 闲鱼 | 阿里巴巴 | SaaS（App / 小程序） | C2C 二手交易（含校园场景子集） | C2C 轻发布交易链路、商品结构化、单库存实时性、信任体系 | 平台免费 + 增值服务 | 阿里云开发者社区架构演进文章、InfoQ 专访、闲鱼云原生文章（SR-01~03） |
| B2 | UU 跑腿 | 河南艾顿（UU 跑腿） | SaaS（App / 小程序） | 同城跑腿：帮取 / 帮买 / 帮送 / 排队代办 | 发单-接单-全程定位-交接确认的跑腿履约链路 | 按单抽佣 | UU 跑腿官网（SR-10） |
| B3 | mall-swarm | macrozheng（开源社区） | 开源自部署（Docker / K8s） | 电商商城（微服务教学向） | Spring Cloud + Spring Cloud Alibaba 全家桶：Nacos 注册/配置、Gateway 网关、Sentinel 熔断、OpenFeign、监控中心 | 开源 + 付费教程/视频课 | GitHub 仓库与技术选型表（SR-04~05） |
| B4 | 校园综合互助开源项目群（campus-secondhand-platform、Campus_used_product_trading_platform、校园二手+失物认领系统、校园综合服务平台等） | GitHub / Gitee / 语雀个人与结对团队 | 开源自部署（单体为主） | 校园二手交易 + 失物招领 + 校园跑腿 + AI 问答（四模块与本项目高度同构） | Spring Boot + MyBatis-Plus + MySQL + Redis 技术栈与本项目基线一致；含抢单、超时转派、DeepSeek AI 助手等实践 | 开源（MIT / MulanPSL-2 等） | GitHub / Gitee / 语雀仓库文档（SR-06~09、SR-11~12、SR-22~23） |

> 选型说明：候选中另有转转、饿了么、RuoYi-Cloud、Spring PetClinic 等，取舍标准为"① 覆盖本项目四大业务场景之一，② 对 Spring Cloud 学习有直接参考价值，③ 资料公开可核实"。PetClinic 未入选标杆清单但作为部署事实来源保留在 §2.3 与 §6。

### 2.2 标杆方案详述

#### 2.2.1 B1 - 闲鱼（阿里巴巴）

| 维度 | 内容 | 置信度 |
| --- | --- | --- |
| 产品定位 | 国内最大的 C2C 闲置物品交易平台，双边市场（买家卖家互相影响规模） | 已核实（SR-03 专访） |
| 目标用户 | 个人卖家与个人买家，轻发布、低门槛 | 已核实（SR-03） |
| 核心能力 | 轻发布（少量图片/短描述即可上架）、C2C 单商品交易链路（无购物车、无多商品聚合订单）、商品结构化、搜索推荐实时性、信任/防欺诈体系 | 已核实（SR-01~03） |
| 架构特点 | 演进路径：单体应用 → 无线化+服务化横向/纵向拆分（业务拆分 + 数据访问收敛 + 公共能力下沉）→ 业务网关收口 → 搜索/推荐/算法平台接入 → Serverless/云端一体。C2C 交易链路特点是"多业务、多状态、多操作"，服务端分三层：底层数据模型、C2X 交易域、业务解决方案 | 已核实（SR-01~03，架构分层为原文表述） |
| 部署形态 | 阿里集团内部基础设施（HSF/ Serversless 平台 GAIA 等），闭源 | 已核实（SR-01~03） |
| 集成方式 | 不开放集成；对外仅产品形态 | 已核实 |
| 定价模式 | 交易免费 + 增值服务 | 综合归纳（公开报道） |
| 优势 | 与本项目"二手交易"模块业务形态完全同源；其"轻发布 → 信息量少 → 商品结构化""单库存售出即下架 → 链路实时性要求高""闲置市场核心是降低信任成本"三条业务洞察可直接映射到校园二手与失物匹配 | 综合归纳 |
| 局限 | 闭源、规模（千万 DAU / GMV 2000 亿）与基础设施（HSF、内部中间件）不可复刻，对学习型项目只有思想参考价值，无代码级参考价值 | 已核实 + 推断 |
| 对本项目的参考价值 | ① 借鉴"单库存 + 状态机 + 实时下架"的交易链路设计；② 借鉴"信任成本"视角设计信用/评价模块；③ 明确"不必追求闲鱼级架构"，校园规模下单体拆 4 个微服务已足够 | 推断 |

**补充事实一：Spring Cloud 单机部署资源基线**（已核实，SR-20~21）
- Spring 官方示例 Spring PetClinic Microservices（8 个微服务 + 网关 + 注册/配置中心 + Prometheus/Grafana/Zipkin 共 11 容器）可用一条 `docker compose up -d` 在本地单机跑通，关键经验是启动顺序（Config Server → Discovery Server → 业务服务）。
- Gitee 项目 spring-cloud-alibaba-dev-env 实测：Spring Cloud Alibaba 开发环境 6 组件（MySQL、Nacos、Sentinel、RocketMQ、Redis、Seata）以 Docker Compose 兼容模式启动共占约 1650MB 内存，其中 Nacos 单独分配 600MB——说明单台 2核4G 轻量服务器可承载微服务基建，但必须裁剪组件并给 JVM 设内存上限。

**补充事实二：Dubbo 与 OpenFeign 的可核实差异**（已核实部分以官方/多来源交叉为准，SR-13~15）
- 定位差异：Dubbo 是完整 RPC 解决方案（通信 + 内置负载均衡/容错/路由治理）；OpenFeign 本质是声明式 HTTP 客户端，治理能力依赖 Spring Cloud 生态（LoadBalancer、Sentinel/CircuitBreaker）。
- 通信差异：Dubbo 默认 TCP 长连接复用 + 二进制序列化（Hessian2/Protobuf，支持 Dubbo/Triple/gRPC/REST 多协议，切换仅需配置）；OpenFeign 基于 HTTP 短连接 + JSON，可开连接池优化。
- 生态差异：Dubbo 原生适配 Nacos/Seata，并提供 sentinel-apache-dubbo-adapter；与 Spring Cloud Alibaba 可共存（dubbo-spring-boot-starter + dubbo-registry-nacos，注解 @DubboService/@DubboReference）。
- 社区存在"Dubbo 比 Feign 快 10 倍"类说法，属单一社区文章观点，量级存在争议，本报告不采信为事实，仅采信"高并发场景 Dubbo 延迟更低"的方向性结论。

**补充事实三：Java LLM 框架定位差异**（SR-16~19）
- Spring AI：Spring 官方生态项目，POJO 优先、ChatClient 流式 API，模型切换靠配置（Portable Service Abstraction），与 Spring Boot 自动配置/依赖注入/可观测性深度整合；适合已有 Spring 工程习惯的团队。
- LangChain4j：分层架构，低阶 API（ChatLanguageModel）+ 高阶 AiServices（注解式接口代理）双模式，模块化灵活、新特性跟进快，但配置复杂、学习曲线较陡，Spring Boot starter 为社区维护。
- Spring AI Alibaba：基于 Spring AI 构建（阿里官方开源），深度对接阿里云百炼/DashScope（Qwen 系列），提供 ReactAgent、多 Agent 编排（Sequential/Parallel/Routing/Loop）、Graph 工作流、MCP、基于 Nacos 的 A2A 通信与动态配置；要求 JDK 17+，与 Spring Cloud Alibaba 同源。
- 用户实习项目已用 Spring AI 2.0 + qwen-plus 完成对话、Function Calling、多 Agent 路由、流式与记忆（material_digest.md D1，§实习经历②），说明 Spring AI 路线对其为"直接复用"，LangChain4j 为"全新实践"。
