## 1. 引言

### 1.1 适用范围与部署形态

**适用范围**：《系统设计》v1.0 冻结的全部运行单元——7 个业务服务（M1 用户与信用 / M2 二手交易 / M3 失物招领 / M4 跑腿拼单 / M5 AI 助手 / M6 通知 / M7 平台管理）+ Spring Cloud Gateway（C-04）+ Nacos（C-03）+ Sentinel Dashboard（C-05）+ Nginx（C-06）+ MySQL 8（C-01）+ Redis 7（C-02），以及按需启动的观测组合（C-07 Prometheus / C-08 Grafana / C-09 Zipkin / C-10 Loki+Promtail）。本文档不新增、不删减任何运行单元。

**部署形态**：公有云**单台轻量云服务器（2核4G 起步）+ Docker Compose**（上游冻结，O5：不做 K8s / 多节点 / 服务网格）。dev 环境运行于开发者本地笔记本，与生产物理隔离。服务器厂商推荐腾讯云轻量应用服务器（校园个人项目预算内；具体厂商、地域、实例规格与资源 ID 待购买后回填，标注**待人工确认**）。

## 2. 环境与资源清单

### 2.1 环境矩阵

| 环境 | 用途 | 集群隔离 | 数据 | 网络访问 |
| --- | --- | --- | --- | --- |
| dev | 开发自测 / 单服务调试 | 本地笔记本（与生产物理隔离），Docker Compose 本地栈 | 模拟数据（本地卷，可随时重建） | 仅 127.0.0.1，禁止连生产数据 |
| int | 前后端 / 多服务联调 | 与 dev 同开发机，独立 Compose project（联调窗口按需启动，project 级隔离） | 模拟数据（独立数据卷） | 仅 127.0.0.1 / 局域网，不出公网 |
| uat | 发布前演示预演与冒烟验收 | 与 prod 同一台云服务器，独立 Compose project + 独立数据卷 + 独立 .env（project 级三元隔离） | 仿生产种子数据 | 经独立端口 8443 HTTPS 访问，安全组限源：仅运维者 IP（T1 信任域约束，对应规则 SG-08，禁 0.0.0.0/0） |
| prod | 生产运行（演示 + 试运行） | 独立 Compose project 常驻（同机唯一常驻完整栈） | 真实数据 | 公网 443（SG-01）+ 80 强制 301 跳转（SG-02）；仅 Nginx 端口映射宿主机 |

**隔离策略说明（单机形态）**：int/uat/prod 三环境共用作"Compose project 级隔离"——独立 project 名（独立容器前缀）、独立 Docker Bridge 网络、独立数据卷、独立 .env 密钥文件；dev 与云端物理隔离（本地笔记本）。禁止 dev 与 prod 共用任何密钥（系统设计 §7.2.3 红线，安全侧复核确认）。mTLS 不启用已由 security-architect 确认（T2 单一信任域内、无跨节点链路，见 §3.2.2）。

**uat 启动窗口策略（经中间确认协议自检未触发，列入人工审核待确认项 H-D2）**：prod 常驻组合约 2.88GB + 系统占用，4GB 内存无法同时承载完整 uat 栈。约定：uat 仅在发布窗口（≤ 30 分钟/次）启动裁剪组合（Gateway + M1/M2/M3/M4 + MySQL + Redis + Nginx，约 1.7GB）；窗口开始前临时 scale=0 停用 prod 非核心容器（M5/M6/M7/Sentinel，L2/L3 功能，降级清单 BD-01~BD-07 已覆盖），窗口结束后立即恢复；窗口需提前在平台公告。

> 环境数量说明：模板要求 dev/int/uat/prod 四环境；《系统设计》§5.1 定义 dev/uat/prod 三环境。本表补齐 int 行的方式为"开发机联调窗口按需启动的独立 Compose project"，不新增任何云资源、不突破内存预算与低成本约束。此取值列入人工审核待确认项 H-D1。

### 3.3 高可用与故障容错

#### 3.3.1 故障域划分

> 单机形态下按四层故障域等价划分（对应企业级单 Pod / 单 Node / 单 AZ / 单 Region 的降维映射）。

| --- | --- | --- | --- |
| 单容器（等价单 Pod） | 单服务实例 | Docker healthcheck（liveness/readiness）+ restart:always 自动重建；网关摘流不杀容器（readiness 失败） | ≤ 1 分钟（进程级） |
| 单中间件（Redis/Nacos，等价单 Node 局部） | 对应能力退化 | restart:always 自动重启 + 降级预案（Redis：BD-03 缓存降级直查 DB、抢单退化 DB 乐观锁；Nacos：已注册实例继续运行、路由不受影响） | ≤ 2 分钟 |
| MySQL 实例（数据域核心） | 全部业务写链路 | restart:always（进程级）；数据级依赖每日备份 + binlog 恢复（§2.2.2） | 进程级 ≤ 1 分钟；数据级 ≤ 30 分钟 |
| 整机（等价单 AZ/Region） | 全部服务 + 全部数据 | 云服务器重装 + 应用/镜像资产 + 对象存储备份回导（SOP 见 §6.2 RB-02 关联预案） | ≤ 4 小时（灾难级，RPO ≤ 24h） |

### 4.5 发布策略

#### 4.5.1 发布方式

全系统采用**滚动发布（单机 Compose 逐容器替换）+ 特性开关（Nacos L2 热更新）**。裁剪说明：蓝绿发布需双倍内存承载新旧两套完整栈（4GB 不可行）；金丝雀需同服务双实例分流量（单机内存预算不允许）；滚动发布为单机形态唯一可行方式，配合 uat 预演窗口 + Nacos 降级开关达到等效风险控制。

| 模块 | 发布方式 | 说明 |
| --- | --- | --- |
| 全部 9 个镜像（M1~M7 + Gateway + Nginx/前端） | 滚动发布（逐容器） | 批次顺序：Nginx/Gateway（入口最后更新）→ M3/M5/M6/M7（L1/L2）→ M1 → M2/M4（L0 核心最后，出问题影响面最小化原则反向：核心先在 uat 验证，prod 最后动） |
| 中间件（MySQL/Redis/Nacos/Sentinel） | 版本升级需停机窗口 + 事先备份 | 中间件不随业务迭代滚动，仅安全补丁/版本升级时操作，走资源变更流程（§4.5.2） |

#### 4.5.2 发布标准流程

- **首次发布（含资源初始化）**：购买服务器 → 基线加固（SSH/安全组 SG-01~SG-08/补丁）→ 安装 Docker/Compose → 配置密钥目录与 .env → 首次 compose up（含 DDL 初始化 docker/sql/ + 管理员种子账号）→ TLS 证书签发 → 冒烟 → 打 v1.0.0 tag → 配置每日备份 cron → 全流程恢复演练 1 次。
- **常规迭代发布**：PR 合入 main → CI 8 阶段（自动）→ uat 预演窗口冒烟（手动触发）→ 生产人工审批 → 逐容器滚动 + 分批观测 → 发布 tag 与公告。
- **资源变更流程**：规格升配/安全组规则变更/域名变更等高危操作——先备份 → 确认回退路径 → 低峰窗口执行 → 验证 → 记录（对齐安全设计 §5.2.4 运维操作窗口约定与 §2.3.3 高敏变更 checklist）。

## 6. 应急与回滚

### 6.1 回滚机制

#### 6.1.1 回滚触发条件

- 生产核心链路（下单/抢单/登录）5xx 错误率 > 5% 持续 5 分钟（AL-01）；
- 核心接口 P99 > 800ms 持续 5 分钟且根因定位为本次发布（AL-03）；
- MySQL/Redis 持续不可访问或余额流水对账出现差额（AL-02 / 对账门禁）；
- 关键 P0/P1 告警触发且 Runbook 缓解无效。

#### 6.1.2 回滚决策人

- On-call（季祥浩，唯一运维者）可独立决定 P0/P1 回滚，无需审批（单人项目回滚授权前置，见 §5.4）；
- P2/P3 回滚由 Owner 评估后决定，原则上纳入当日或周内处理。

#### 6.1.3 回滚执行 SOP

| 对象 | 回滚方式 | 预计耗时 | 有损风险 / 数据丢失 |
| --- | --- | --- | --- |
| 应用版本 | SSH → docker compose 指定上一镜像 tag 重新 up（逐容器或全栈，按 §4.5.3 批次反向回滚） | ≤ 5 min | 无（DDL 兼容前提下） |
| 配置（L2 Nacos） | Nacos 控制台回退历史版本（保留最近 10 个版本） | < 1 min | 无 |
| 配置（L3/L4 .env） | 服务器密钥目录上一版本副本恢复（变更前 cp 备份） | < 2 min | 无（轮换窗口内） |
| 前端静态资源 | Nginx 镜像回退上一版本 | ≤ 5 min | 无 |
| 数据库 | DDL 变更必须可回滚（提供反向脚本）；**不可回滚 DDL（DROP COLUMN/TRUNCATE 等）禁止与代码同发布，须前置变更并单独备份**；数据级回滚 = dump 回导 + binlog 重放 | DDL 回滚 < 10 min；全库恢复 ≤ 30 min | 有（恢复点之后数据丢失，受 RPO 约束） |

MVP 阶段不可回滚 DDL 清单：**无计划项**（全新系统、表结构一次成型；若迭代期出现，按上表前置流程执行并提前公告）。

#### 6.2.2 Runbook 编写规范

每条 Runbook 按四段结构编写：**症状**（可观测特征：大盘指标/告警内容/用户反馈）→ **诊断**（按顺序执行的定位步骤，明确工具与查询路径）→ **缓解**（分场景处置动作，与回滚 §6.1、降级 BD-01~BD-07、限流、恢复机制衔接）→ **升级**（缓解未生效的升级条件、路径与对外通告机制）。存放于仓库 docs/runbook/ 目录，与告警编号一一对应。

#### 6.2.3 RB-01：核心链路 5xx 错误率突增

- **症状**：AL-01 触发；服务健康大盘 M1/M2/M4 RED 面板 5xx 曲线抬升；学生端表现为下单/抢单/登录失败提示。
- **诊断（按顺序执行）**：
  1. Grafana 服务健康大盘定位错误集中在前端入口（Gateway）还是单一业务服务（按服务过滤 error 率）；
  2. Loki 检索该服务最近 ERROR 日志（按 traceId 下钻 Zipkin 全链路），区分：依赖超时（MySQL/Redis）/ OOM 重启（docker ps 看 RESTARTS 计数）/ 本次发布引入（对照发布时间线）；
  3. docker stats 核对该容器内存是否触顶 -Xmx（联动 RB-05）。
- **缓解**：
  - 场景 A（本次发布引入）→ 按 §6.1.3 回滚该批次容器至上一镜像 tag；
  - 场景 B（依赖故障）→ 转对应 Runbook（MySQL → RB-02；Redis → 容器自动重启 + BD-03 降级已兜底）；
  - 场景 C（流量突增/攻击）→ Nacos 临时下调限流阈值（L2 热更新）+ 确认安全组与 AL-08；
  - 场景 D（单容器异常循环重启）→ docker compose restart 该服务；仍复现则回滚镜像。
- **升级**：缓解后 15 分钟内 5xx 未回落 → 全栈回滚至上一版本并平台公告；数据疑似受损 → 立即停写 + 转 RB-02 数据恢复预案，公告止损窗口。
