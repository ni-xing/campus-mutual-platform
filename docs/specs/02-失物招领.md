# 02 失物招领模块 Spec

> 上位约束见 `00-全局约定.md`。

## 1. 用户故事

- 作为拾获者，我要发布拾获信息（物品、地点、时间、照片），让失主找到我。
- 作为失主，我要发布寻物启事，并浏览拾获信息匹配我的物品。
- 作为失主，我要发起认领请求，通过描述验证后拿回物品。

## 2. 功能需求

| 编号 | 功能 | 说明 |
|---|---|---|
| L-01 | 发布拾获信息 | 必填：物品名称、拾获地点(楼栋级)、拾获时间、描述；图片 ≤ 3 张 |
| L-02 | 发布寻物启事 | 必填：物品名称、丢失时间段、特征描述 |
| L-03 | 列表与筛选 | 拾获/寻物两个 tab；按物品分类 + 地点 + 时间倒序筛选；走 Redis 缓存 |
| L-04 | 关键词匹配提示 | 发布寻物启事后，系统按物品名称/分类匹配近 7 天拾获信息，在详情页展示"可能匹配"列表（纯 SQL LIKE + 分类匹配，不引入 ES） |
| L-05 | 认领流程 | 失主对某拾获信息发起认领，填写物品特征证明；拾获者确认/拒绝 |
| L-06 | 状态机 | 拾获信息：待认领 → 认领中 → 已归还 / 已关闭；寻物启事：寻找中 → 已找到 / 已关闭 |
| L-07 | 站内通知 | 认领发起、确认、拒绝时，系统消息通知对方（复用站内消息表） |
| L-08 | 联系方式脱敏 | 认领确认前，双方手机号互相不可见；确认后可见（脱敏规则见全局约定） |

MVP 裁决：不做图像识别自动匹配，关键词匹配（L-04）即为上限。

## 3. 验收标准

- AC-1：Given 拾获信息"黑色水杯-图书馆"，When 失主发布寻物"水杯-图书馆附近"，Then 寻物详情页出现该拾获信息于"可能匹配"。
- AC-2：Given 失主发起认领，When 拾获者确认，Then 拾获信息变"已归还"，寻物启事变"已找到"，双方收到通知并互见脱敏后的联系方式。
- AC-3：Given 拾获信息已"认领中"，When 第二位失主发起认领，Then 提示"该物品正在认领中"，不产生第二条待处理认领。
- AC-4：Given 拾获者拒绝认领，Then 信息回"待认领"，失主收到拒绝通知。
- AC-5：Given 未登录用户，When 访问发布接口，Then 返回 401 语义错误码；列表接口可匿名浏览。
- AC-6：Given 拾获信息发布超过 30 天未认领，When 定时任务执行，Then 自动置为"已关闭"并通知发布者。

## 4. 边界与异常

- 认领证明文本 ≤ 300 字，必填。
- 同一失主对同一拾获信息只能有一个待处理认领。
- 关闭/已归还的信息不可再发起认领。

## 5. 数据模型（物理表，lostfound_db / notify_db，已落地）

- `lost_item` → `t_lost_item`：id, type(拾获/寻物), publisher_id, name, category, location, happened_at, description, images, status + 审计字段
- `claim` → `t_claim_apply`：id, lost_item_id, claimant_id, proof, status(待处理/已确认/已拒绝), created_at
- `notification` → `t_notice`（notify_db）：id, user_id, title, content, read_flag, created_at
- 附：`t_lost_item_archive`（30 天过期归档）、`t_outbox_event`（认领事件 → 通知投递）

## 6. 任务拆解

1. 建表 + 实体/Mapper
2. 拾获/寻物发布 + 列表筛选（Redis 缓存）
3. 关键词匹配提示（LIKE + 分类）
4. 认领流程 + 状态机
5. 站内通知（复用消息表）
6. 30 天过期定时任务
7. 按 AC-1~6 写验收测试
