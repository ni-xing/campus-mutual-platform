# 03 跑腿拼单模块 Spec

> 上位约束见 `00-全局约定.md`。拼单采用方案 B：MVP 轻量形态 = 跑腿单 + 拼车备注字段，完整拼单匹配能力延后。

## 1. 用户故事

- 作为发单人，我要发布跑腿单（取/送地点、物品描述、酬金），等同学接单。
- 作为接单员，我要浏览可接跑腿单，抢单后完成配送并获得酬金。
- 作为拼车需求者，我在跑腿单里用"拼车备注"标注"可拼"，顺路的同学自行联系（MVP 不做系统撮合）。

## 2. 功能需求

| 编号 | 功能 | 说明 |
|---|---|---|
| E-01 | 发布跑腿单 | 必填：类型(取件/代买/代送)、取/送地点(楼栋级)、物品描述、酬金(1-100元)、截止时间；可选：拼车备注(≤50字，标注"可拼/求拼") |
| E-02 | 跑腿大厅 | 待接单列表，按酬金/发布时间排序；走 Redis 缓存 |
| E-03 | 抢单 | 校验：单子仍待接、发单人 ≠ 接单人、接单员当日接单 < 10；抢单用 Redis/数据库原子操作防重复接单 |
| E-04 | 状态机 | 待接单 → 进行中 → 待确认(接单员标记送达) → 已完成 / 已取消 |
| E-05 | 酬金结算 | 发布跑腿单时冻结酬金（从余额预扣）；完成确认后入接单员余额；取消时解冻退回 |
| E-06 | 超时处理 | 截止时间到仍"待接单"自动取消并退回酬金（定时任务） |
| E-07 | 评价 | 已完成后发单人对接单员评 1-5 星，计入接单员信用分 |
| E-08 | 拼车备注 | 仅作为文本展示与筛选条件（"仅看可拼"过滤），MVP 不做匹配算法 |

## 3. 验收标准

- AC-1：Given 发布人余额 ≥ 酬金，When 发布跑腿单，Then 生成单子且余额冻结相同金额。
- AC-2：Given 两个接单员同时抢同一单，When 并发抢单，Then 仅一人成功，状态变"进行中"，另一人收到"已被接单"。
- AC-3：Given 跑腿单"进行中"，When 接单员标记送达且发单人确认，Then 状态变"已完成"，冻结酬金入接单员余额。
- AC-4：Given 跑腿单"待接单"且已过截止时间，When 定时任务执行，Then 自动取消、冻结酬金退回发布人余额、发布人收到通知。
- AC-5：Given 发布人尝试接自己的单，When 抢单，Then 拒绝并提示。
- AC-6：Given 接单员当日已接 10 单，When 再抢，Then 拒绝并提示"已达当日上限"。
- AC-7：Given 勾选"仅看可拼"，When 查询列表，Then 仅返回拼车备注非空的单子。

## 4. 边界与异常

- 酬金范围 1-100 元，两位小数。
- 发单人取消"进行中"的单需接单员同意（MVP：直接协商，系统提供取消入口，双方收到通知，酬金退回）。
- 信用分低于阈值（< 3.0 均分）的接单员在大厅排序降权（MVP 简化为排序因子）。

## 5. 数据模型（物理表，errand_db，已落地）

- `errand` → `t_errand_order`：id, publisher_id, type, pickup_loc, deliver_loc, description, reward, status, carpool_note, deadline, taker_id, created_at + 审计字段
- `errand_settle` → 酬金冻结/入账/退回统一落 trade_db 的 `t_balance_flow`（跨域资金流，复用 01 的余额体系）；抢单动作另有 `t_grab_record` 留痕
- `credit` → 不建独立信用表，直接读写 user_db 的 `t_user_account.credit_score`（初始 100，区间 [0,200]）；评星到增减的映射见 05-用户与认证 §4；「均分 <3.0 降权」等效实现为 credit_score 低于阈值的排序降权
- 附：`t_errand_subtask`（拼车子任务预留）、`t_errand_order_archive`、`t_outbox_event`

## 6. 任务拆解

1. 建表 + 实体/Mapper
2. 发布（含余额冻结事务）
3. 跑腿大厅列表 + 可拼筛选（Redis 缓存）
4. 原子抢单（防并发重复接单）
5. 送达确认 + 酬金结算状态机
6. 超时取消定时任务
7. 评价与信用分
8. 按 AC-1~7 写验收测试
